# 真实门店投运清单 / 不可省略的验收门槛

当前版本的 **SELF_SERVICE_STAGING_GATE=PASS（基于本地自动化，不代表实机）**，**STAFFED_LIVE_PAYMENT_GATE=NOT_VERIFIED**，**UNATTENDED_PRODUCTION_GATE=BLOCKED**。

## A. 有人值守支付试点门槛

- [ ] 具备有效经营主体、商户号和获批的微信 Native 支付产品权限。支付域名、回调域名和公网 HTTPS 均正确。
- [ ] 使用真正的商户证书与平台公钥在隔离环境验证创建/查询/关单，含签名探测/错误签名拒绝、重复回调、金额错、退款、账单核对与超时。
- [ ] 为退款、订单异常、`PAYMENT_REVIEW`、`PAYMENT_PENDING` 设定负责人员与处理时限；缺少完整退款流程不得自行宣布可正式收费。
- [ ] 管理员使用强密码、HTTPS、VPN/私有入口、定期密钥轮换，支付公钥证书更换和非敏感日志；公开入口不允许访问后台 API。
- [ ] 所有数据有可验证的异地备份与至少一次实际恢复演练；断电/恢复后一致性验证。
- [ ] 真实采购/商品/价格/库存基础资料核对，退货、税务、票据、商品限售与线上销售合法性核查。
- [ ] 浏览器兼容性（顾客真实手机/微信/支付宝环境）及现场网络、断网、重复点击、支付回调延迟、摄像头权限实测。

## B. 24小时真正无人值守的额外硬门槛（本源码未完成）

- [ ] 明确扫码进店认证提供商，具备真实手机号或其他合规验证流程，并获得隐私政策和必要的用户授权。共享静态 QR 并不能认证进店者。
- [ ] 采购适合门型的商业门禁、出门机械/电气应急释放、门磁、UPS；由当地合格人员审核消防疏散、停电断网状态，现场签字。
- [ ] 实现门禁控制器正式 SDK、设备状态反馈与认证授权关联，进行故障注入和防尾随测试。**付款不得作为出门必要条件**。
- [ ] 监控布局、录像存储、远程人工值守和求助通道有专人负责，能在设备失联/掉线/断电时响应；不能把人形检测等同防盗。
- [ ] 完成顾客未扫码商品、漏扫、多件叠放、尾随、支付失败、网络中断、老人/儿童等场景的实际损耗风险评估。
- [ ] 在人工值守下运行一段完整试运营周期，记录订单、真实收款、库存与实际损耗偏差，制定开店/停用与应急恢复 SOP。

## C. 源码验收证据和未验证事项

- Python 测试验证了 SQLite 单实例事务、库存预留/释放、登录 CSRF、身份邀请码一次性、支付通知 RSA/AES 验签、去重、对账恢复、迁移和 Frigate 事件接口。
- 微信支付测试使用人工生成的离线 RSA 测试密钥与 MockTransport；**没有连接真实微信商户、没有真实资金、没有实际证书轮换或退款。**
- 尚未在真实 Docker Engine、实际 RTSP 摄像头/Frigate、Home Assistant/ESPHome 设备、真实移动手机和店面网络完成完整 E2E。浏览器运行环境可能限制 localhost 导航，不应把静态页面检查当成设备验收。
- 真实店铺地址、门体形式、支付商户资质、现有收银系统和当前消防要求尚不确定，无法独立进行最终放行。
