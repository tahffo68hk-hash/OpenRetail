# 技术路线

依据是 2026-11-06 读过并跑过的代码，不是一份已批准的建设计划。完全无人值守保持 NOT_APPROVED。真实支付和实体开锁保持关闭，直到店主对具体商户和具体门体另作批准。

店内运行放在店里的本地计算机上。这台开发用云虚拟机只适合读代码和跑测试，不适合当门店主机：它没有 Docker 引擎，没有摄像头，也没有店内网络。

## 建议（不是已决定的事实）

单店、大约 20–50㎡ 的 v1，**建议继续用 OpenRetail 自己的 SQLite 作为库存权威**。

理由只来自现状：下单、预留、扣减和流水已经在这一份 SQLite 里用 `BEGIN IMMEDIATE` 串行完成；有订单后会拒绝 CSV 全量盖库存；ERPNext 客户端显式 `ready_for_sale=false`；OSPOS 没有已合并的稳定外部 API（PR #4408 在查阅当日仍是 open）。再上一个 ERP 会变成第二本账。

以后可以把 OSPOS 做成适配器或收银交换，但只在它的数据模型和一条真实可运行的集成路径明显省下成月工作时才做。现在不要引入 ERPNext。**店主仍要自己决定权威源。** 在决定写下之前，`DECISIONS.md` 把这件事标成开放。

## 顺序

### 1. 支付联调，仍然不产生真实扣款

先做完不碰顾客资金的路径：保持 demo 的 `MOCK_NOT_REAL_MONEY` 与 `verified=0` 区分；用本地密钥把 Native 下单、回调验签、重复通知、金额/商户不符、查单和关单再跑一遍。官方文档指向的是正式域名 `api.mch.weixin.qq.com`。本次没有确认免扣款沙箱，所以不要把 `MockTransport` 说成沙箱已通过。

店主批准商户材料之后，才在隔离环境做第一笔可撤销的真实联调。同时补上退款和日终账单，这两项官方流程里有、本仓库没有。支付宝、JSAPI、小程序和 H5 都还没写，不要在文档里假装已接通。

### 2. 库存完整性

保持单一写入路径：预留下单、取消或未进入支付网关的超时释放、支付成功同事务扣减、`PAYMENT_PENDING` 在查单确认 `CLOSED` 之前不释放。备份继续用 SQLite 在线备份，恢复继续写到另一个文件。

商品主数据如果来自 OSPOS，只导入一次或逐条调整，不双写。不要为了「更完整」部署 ERPNext。

### 3. 顾客侧体验（有人值守）

现有页面支持扫码枪输入、部分浏览器的 `BarcodeDetector`、服务端定价和模拟支付。2026-11-06 的桥接脚本在补上演示环境变量后跑通了「建会话 → 加商品 → 下单 → 模拟支付 → 管理员登录」。干净工作区直接跑该脚本会因导入时缺少密钥而失败，应先修脚本的启动方式，再谈公网验收。

真机验收仍缺：顾客手机、微信内打开、HTTPS、重复点击和回调延迟。Native 二维码设计给另一台屏幕，不是手机里的 JSAPI。

### 4. 虚拟门禁，仍然不驱动真实锁

可以继续做只读信号：Home Assistant 连通性、官方 `binary_sensor` 门磁状态、ESPHome 只读示例。`unlock()` 保持模拟或拒绝。不要调用官方 `lock.unlock` / `lock.open`。应急出门不依赖支付，也不依赖 ESP32。

### 5. 监控

Frigate 保持本地 NVR。MQTT 只接收活动元数据。`person` 可以显示为「有人」，不能显示为「盗窃」或「未付款离店」。worker 尚未对真实 broker 运行；它目前不转发 `update`。付费检测模型不要开。

## 明确排后或不做

- 不把这台云虚拟机当成门店生产环境，也不为它购买云套餐。
- 不在 v1 做多店高可用数据库。SQLite 这条限制写在 `database.py` 的模块说明里。
- 不在无人值守获批前做进店身份供应商或电锁 SDK。获批本身不是这条路线图能给出的。
