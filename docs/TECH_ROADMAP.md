# 技术路线

依据是 2026-11-06 读过并跑过的代码，不是一份已批准的建设计划。完全无人值守保持 NOT_APPROVED。真实支付和实体开锁保持关闭，直到店主对具体商户和具体门体另作批准。

店内运行放在店里的本地计算机上。这台开发用云虚拟机只适合读代码和跑测试，不适合当门店主机：它没有 Docker 引擎，没有摄像头，也没有店内网络。

## 已决定

2026-11-06 店主决定：库存系统权威是本仓库的 SQLite。OSPOS 与 ERPNext 都不得变成第二套权威、各自扣减同一库存。OSPOS 以后只可以作为可选适配器再评估。现在不部署 ERPNext。

## 顺序

### 1. 支付联调，仍然不产生真实扣款

演示沙箱已经具备，并且 pytest 覆盖了这些本地行为：查单、关单、`mock:` 单超时释放、`mock-notify` / `mock-confirm` 幂等、模拟退款把 SQLite 库存加回。付款记录保持 `MOCK_NOT_REAL_MONEY` 和 `verified=0`。这条路径不调用 `api.mch.weixin.qq.com`。

尚未做到：微信商户联调、微信退款、日终账单。官方文档指向正式域名。本地 `MockTransport` 和 `mock:` 沙箱都不是微信沙箱验收。支付宝、JSAPI、小程序和 H5 都还没写。

店主批准商户材料之后，才可以做第一笔可撤销的真实联调。

### 2. 库存完整性

权威账本就是这份 SQLite。已有流水：期初 `OPENING_BALANCE`、预留、取消释放、支付扣减 `PAID_SALE`、模拟关单、模拟超时、模拟退款 `MOCK_REFUND_RESTORE`。`GET /api/admin/inventory-ledger` 用流水合计核对账面。并发抢库存、取消、扣减和退款回补已有测试。

微信 `PAYMENT_PENDING` 在查单确认关闭之前仍不因计时器释放。备份继续用 SQLite 在线备份，恢复继续写到另一个文件。

若将来做 OSPOS 适配器，它只能交换数据，不能自己再扣一遍本店库存。不要为了「更完整」部署 ERPNext。

### 3. 顾客侧体验（有人值守）

现有页面支持扫码枪输入、部分浏览器的 `BarcodeDetector`、服务端定价和模拟支付。`scripts/ui_bridge_smoke.py` 在不设置 `ADMIN_KEY`、`INTEGRATION_KEY`、`APP_SECRET` 时可以跑通「建会话 → 加商品 → 下单 → 模拟支付 → 管理员登录」。这仍是 Chrome 接到 TestClient 的桥，不是公网验收。管理页已有「模拟退款」：第一次成功提示「模拟退款已回补库存，不是微信退款」；已经退过后再请求是幂等的，提示「模拟退款已经完成，这次没有增加库存」。顾客页没有退款按钮。

真机验收仍缺：顾客手机、微信内打开、HTTPS 和回调延迟。本地页面现在会忽略一部分进行中的第二次点击，这还不是手机上的验收。Native 二维码设计给另一台屏幕，不是手机里的 JSAPI。

### 4. 虚拟门禁，仍然不驱动真实锁

可以继续做只读信号：Home Assistant 连通性、官方 `binary_sensor` 门磁状态、ESPHome 只读示例。`unlock()` 保持模拟或拒绝。不要调用官方 `lock.unlock` / `lock.open`。应急出门不依赖支付，也不依赖 ESP32。

### 5. 监控

Frigate 保持本地 NVR。MQTT 只接收活动元数据。`person` 显示为「有人」，不能显示为「盗窃」「偷盗」或「未付款离店」。worker 对 `label=person` 的 `new`、`update`、`end` 会转发，其他 label 不转发。它尚未对真实 broker 运行，也不需要先有一台 broker。付费检测模型不要开。

## 明确排后或不做

- 不把这台云虚拟机当成门店生产环境，也不为它购买云套餐。
- 不在 v1 做多店高可用数据库。SQLite 这条限制写在 `database.py` 的模块说明里。
- 不在无人值守获批前做进店身份供应商或电锁 SDK。获批本身不是这条路线图能给出的。
- 不把 OSPOS 或 ERPNext 接成会自行扣库存的第二本账。
